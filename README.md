# Library Book Rental System

A Django project for recording who borrowed which book, with pages to list, add, edit and delete rentals, automatic overdue status and fines, an admin screen and a login-protected REST API.

## Quick start

```
pip install django djangorestframework mysqlclient python-dotenv
copy .env.example .env        # then fill in your own values
python manage.py makemigrations
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

| URL | What it shows |
| --- | --- |
| `/` | Welcome page |
| `/Book_rental_list/` | All rentals |
| `/Add_rental/` | Add form |
| `/admin/` | Admin |
| `/api/` | API root (login required) |

Run `python manage.py test` after every change. Run `python manage.py update_overdue` once a day.

# Full walkthrough

This project lets a librarian record who borrowed which book, see every rental, edit or delete it, and have overdue status and fines calculated automatically. Every page you click follows the same path through the same eight files, and this guide walks through them in the order you build them.

## The big picture

The project has one Django project (`LBRS_Project`, the settings and the main URL file) and one app (`BookRental_app`, your actual feature). Every page request travels the same road:

1. The browser asks for a URL, for example `/Book_rental_list/`.
2. `LBRS_Project/urls.py` receives it and passes it to the app with `include()`.
3. `BookRental_app/urls.py` matches the URL to a view and gives the route a name.
4. The view in `views.py` gets data from the model (the database) and picks a template.
5. The template in `Templates/` mixes the data into HTML.
6. Django sends that HTML back, and the browser shows the page.

If you remember one rule, make it this one: **a name written in one file must be spelled exactly the same in the file that uses it.** Most Django errors, including `NoReverseMatch`, are a spelling mismatch.

## Where each file fits

| File | Job | You write it |
| --- | --- | --- |
| `LBRS_Project/settings.py` | Registers apps, template folder, database, static files | Edit what Django generated |
| `LBRS_Project/urls.py` | Main URL file, hands everything to the app | Edit |
| `BookRental_app/models.py` | Describes the database table | Edit |
| `BookRental_app/migrations/` | Instructions that build the table | Generated by `makemigrations` |
| `BookRental_app/forms.py` | Builds the HTML form from the model and checks the input | Create |
| `BookRental_app/serializers.py` | Same job for the API (JSON instead of HTML) | Create |
| `BookRental_app/views.py` | The logic for every page | Edit |
| `BookRental_app/urls.py` | Maps URLs to views and names them | Create |
| `Templates/*.html` | The pages the user sees | Create |
| `static/` | CSS and JavaScript | Create |
| `BookRental_app/admin.py` | Lets you manage data at `/admin/` | Edit |
| `BookRental_app/tests.py` | Automatic checks that the code works | Edit |
| `.env` | Secret key and database password, kept out of the code | Create, never share it |

## Part 1: Creating the project and the app

A project is the whole website; an app is one feature inside it. One project can hold many apps, and yours holds one.

Run these two commands in the terminal, in this order:

```
django-admin startproject LBRS_Project .
python manage.py startapp BookRental_app
```

The `.` at the end of the first command puts `manage.py` next to the `LBRS_Project` folder. Without it you get an extra nested folder. `manage.py` is the tool you run everything through: `runserver`, `makemigrations`, `migrate`, `createsuperuser`, `test`.

`startapp` creates `models.py`, `views.py`, `admin.py`, `apps.py` and `tests.py`. It does not create `urls.py` or `forms.py`, so you add those two files yourself.

### Register the app in settings.py

This is the step people forget. In `LBRS_Project/settings.py`:

```python
INSTALLED_APPS = [
    'django.contrib.admin',
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    'django.contrib.messages',
    'django.contrib.staticfiles',
    'BookRental_app',
    'rest_framework',
]
```

The text `'BookRental_app'` must match the app's folder name exactly. If you leave it out, `makemigrations` says "No changes detected" and your model never becomes a table. `rest_framework` is a separate package you installed, and it must be listed as well or the API fails.

### The other settings you use

| Setting | What it does | Must match |
| --- | --- | --- |
| `ROOT_URLCONF = 'LBRS_Project.urls'` | The first URL file Django reads | The file `LBRS_Project/urls.py` |
| `TEMPLATES` → `'DIRS': [BASE_DIR / "Templates"]` | Tells Django where your HTML files are | The real folder name `Templates` |
| `'APP_DIRS': True` | Also looks for a `templates` folder inside each app | Not used by you, but harmless |
| `context_processors.request` | Makes `request` available inside templates | Needed if a template uses `request.path` |
| `STATIC_URL` and `STATICFILES_DIRS` | Where CSS and JS live and how `{% static %}` finds them | The real folder `static/` |
| `DATABASES` | MySQL, with the login read from `.env` | The names in your `.env` file |
| `TIME_ZONE = 'Asia/Kolkata'` | The zone used to show dates and times | Used by `timezone.localdate()` in the model |
| `REST_FRAMEWORK` | Makes the API require a login | The exact name `REST_FRAMEWORK` |

### Keeping secrets out of the code

`settings.py` reads the secret key and database login with `os.environ[...]`, after `load_dotenv(BASE_DIR / '.env')` loads the `.env` file. The `.env` file holds `SECRET_KEY`, `DEBUG`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST` and `DB_PORT`. It is listed in `.gitignore`, so Git never commits it, and you should never zip or send it.

A useful check at any time: run `python manage.py check`. It should print "System check identified no issues."

## Part 2: models.py and migrations

The model is the first real code you write. One class is one database table, and each line inside it is one column. Everything else in the project (form, API, views, templates) reads these field names, so spell them carefully.

```python
from decimal import Decimal

from django.core.validators import MinValueValidator
from django.db import models
from django.utils import timezone

STATUS_CHOICES = [
    ('Borrowed', 'Borrowed'),
    ('Returned', 'Returned'),
    ('Overdue', 'Overdue'),
    ('Lost', 'Lost'),
]

FINE_PER_DAY = Decimal('5.00')   # change this to your own rate


class BookRental(models.Model):
    book_title = models.CharField(max_length=100)
    author_name = models.CharField(max_length=100)
    borrower_name = models.CharField(max_length=100)
    borrower_email = models.EmailField()
    return_date = models.DateField()
    rental_date = models.DateField()
    fine_amount = models.DecimalField(
        max_digits=20, decimal_places=2, default=0.00,
        validators=[MinValueValidator(0)],
        editable=False,
    )
    returned_date = models.DateField(null=True, blank=True, editable=False)
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)
    status = models.CharField(max_length=20, choices=STATUS_CHOICES, default='Borrowed')

    def __str__(self) -> str:
        return self.book_title

    def update_status_and_fine(self):
        if self.status == 'Lost':
            return                      # a lost book stays as it is

        today = timezone.localdate()

        if self.status == 'Returned':
            if self.returned_date is None:
                self.returned_date = today
            end_date = self.returned_date
        else:
            self.returned_date = None
            end_date = today
            self.status = 'Overdue' if today > self.return_date else 'Borrowed'

        late_days = max((end_date - self.return_date).days, 0)
        self.fine_amount = late_days * FINE_PER_DAY

    def save(self, *args, **kwargs):
        self.update_status_and_fine()
        super().save(*args, **kwargs)
```

### The fields

| Field | Type | What it means |
| --- | --- | --- |
| `book_title`, `author_name`, `borrower_name` | `CharField(max_length=100)` | Short text, up to 100 characters |
| `borrower_email` | `EmailField()` | Text that must look like an email address |
| `rental_date` | `DateField()` | The day the book was taken |
| `return_date` | `DateField()` | The due date. The code treats it as the day the book must come back |
| `fine_amount` | `DecimalField` | Money, 2 decimal places. Calculated, not typed (`editable=False`) |
| `returned_date` | `DateField(null=True, blank=True)` | The day it was actually returned. Empty until then |
| `created_at` | `DateTimeField(auto_now_add=True)` | Set once, when the row is first saved |
| `updated_at` | `DateTimeField(auto_now=True)` | Set again on every save |
| `status` | `CharField(choices=...)` | One of the four words in `STATUS_CHOICES`, default `Borrowed` |

Three details worth knowing:

- `editable=False` removes a field from every form and makes it read-only in the API. The code, not the user, fills it.
- `STATUS_CHOICES` is a list of pairs: the value stored in the database, and the label shown to people. You gave both the same text.
- Django adds an `id` column on its own. It is the number used in `Rental_detail/<int:rid>/`.

### The fine logic

`save()` runs every time a rental is saved, whether from the form, the admin or the API. Yours calls `update_status_and_fine()` first, then the normal `super().save()`. The method works like this:

- **Lost:** nothing changes.
- **Returned:** today's date is stored in `returned_date` the first time. The fine is the number of days between the due date and that day, times the rate. It stops growing after that.
- **Anything else:** the status becomes `Overdue` if today is after the due date, otherwise `Borrowed`. The fine is the days late times the rate.

The rate is `FINE_PER_DAY`, currently 5.00. Change that one line to change the rate everywhere.

### Migrations: turning the class into a table

A model on its own does nothing until you run two commands:

```
python manage.py makemigrations
python manage.py migrate
```

- `makemigrations` compares your models with the last migration and writes a new file in `BookRental_app/migrations/` (for example `0001_initial.py`). It only writes instructions.
- `migrate` runs those instructions against MySQL and builds or alters the table.

Run both commands every time you change a field. If you change `models.py` and skip them, the page fails with an error like "Unknown column". Never edit a migration file by hand, and never delete one after you have used it.

## Part 3: forms.py and serializers.py

Both files take your model and turn it into something a user or a program can send data through. The form does it for web pages (HTML), and the serializer does it for the API (JSON). Both check the data before it reaches the database.

### forms.py

```python
from django.forms import ModelForm, DateInput
from .models import BookRental

class BookRentalForm(ModelForm):
    class Meta:
        model = BookRental
        fields = "__all__"
        widgets = {
            'rental_date': DateInput(attrs={'type': 'date'}, format='%Y-%m-%d'),
            'return_date': DateInput(attrs={'type': 'date'}, format='%Y-%m-%d'),
        }

    def clean(self):
        cleaned = super().clean()
        rental, ret = cleaned.get('rental_date'), cleaned.get('return_date')
        if rental and ret and ret < rental:
            self.add_error('return_date', 'Return date cannot be before rental date.')
        return cleaned
```

- `ModelForm` builds one form field for each model field. You do not write the HTML inputs yourself.
- `model = BookRental` tells it which model to read. The name must match the class in `models.py`.
- `fields = "__all__"` means every editable field. `fine_amount`, `returned_date`, `created_at` and `updated_at` are not editable, so they are left out automatically.
- `widgets` changes how a field looks. `type: date` shows a calendar. The dictionary keys (`'rental_date'`, `'return_date'`) must match the model field names exactly.
- `clean()` runs after each field has passed its own check. It compares the two dates, and `add_error('return_date', ...)` shows the message next to the return date box.

### serializers.py

```python
from rest_framework import serializers
from .models import BookRental

class BookRentalSerializers(serializers.ModelSerializer):
    class Meta:
        model = BookRental
        fields = '__all__'

    def validate(self, data):
        rental = data.get('rental_date', getattr(self.instance, 'rental_date', None))
        ret = data.get('return_date', getattr(self.instance, 'return_date', None))
        if rental and ret and ret < rental:
            raise serializers.ValidationError(
                {'return_date': 'Return date cannot be before rental date.'})
        return data
```

- It has the same structure as the form: a `Meta` class with the model and the fields.
- With `'__all__'`, the non-editable fields (`fine_amount`, `returned_date`) appear in the JSON output but cannot be written by the client.
- `validate()` does the same date check as the form's `clean()`.
- `data.get('rental_date', getattr(self.instance, ...))` is the fix for partial updates. If the client sends only one field, the missing date is read from the saved record instead. Without this, a PATCH that sends only `status` crashes with a `KeyError`.

### Why both files exist

The form is used by the web pages (`Add_rental`, `Update_rental`). The serializer is used by the API (`BookRentalViewSet`). You need the date check in both, because either one can be the way data arrives.

## Part 4: views.py

A view is a Python function or class that receives the browser's request and returns a response. Your file has three kinds: function views for the read-only pages, class views for add, edit and delete, and one API viewset.

```python
from django.shortcuts import render, get_object_or_404
from django.urls import reverse_lazy
from django.views.generic import CreateView, UpdateView, DeleteView
from rest_framework import viewsets

from .forms import BookRentalForm
from .models import BookRental
from .serializers import BookRentalSerializers


def Home(request):
    return render(request, 'Home.html')

def Book_rental_list(request):
    bookrental = BookRental.objects.order_by('-created_at')
    return render(request, 'Book_rental_list.html', {'RBooks': bookrental})

def Rental_detail(request, rid):
    bookrental = get_object_or_404(BookRental, id=rid)
    return render(request, 'Rental_detail.html', {'bookrental': bookrental})


class Add_rental(CreateView):
    model = BookRental
    form_class = BookRentalForm
    template_name = 'form.html'
    success_url = reverse_lazy('bookrental')

class Update_rental(UpdateView):
    model = BookRental
    form_class = BookRentalForm
    template_name = 'form.html'
    success_url = reverse_lazy('bookrental')

class Delete_rental(DeleteView):
    model = BookRental
    template_name = 'delete.html'
    context_object_name = 'bookrental'
    success_url = reverse_lazy('bookrental')

class BookRentalViewSet(viewsets.ModelViewSet):
    queryset = BookRental.objects.order_by('-created_at')
    serializer_class = BookRentalSerializers
```

### Function views

- Each takes `request` first. `render(request, 'file.html', {...})` loads a template from `Templates/`, fills it with the dictionary, and returns the HTML.
- `Home` sends no data, so it only shows the page.
- `Book_rental_list` asks the model for every rental, newest first (`order_by('-created_at')`), and sends them to the template under the key `'RBooks'`.
- `Rental_detail` has an extra parameter, `rid`. Django fills it from the URL (`<int:rid>`). `get_object_or_404` returns that rental, or shows a 404 page if the id does not exist, so the site does not crash on a wrong number.

### Class views

Django's generic views already know how to show a form, check it and save it. You only fill in the settings:

| Setting | Meaning |
| --- | --- |
| `model` | Which table to work on |
| `form_class` | Which form to show and validate |
| `template_name` | Which HTML file to render (`form.html` is shared by add and edit) |
| `success_url` | Where to go after saving. `reverse_lazy('bookrental')` turns the route name into a URL |
| `context_object_name` | The name the template uses for the object (`delete.html` uses `bookrental`) |

Both `UpdateView` and `DeleteView` find the record from `<int:pk>` in the URL. The URL parameter must be called `pk` exactly, or Django cannot find the record.

These views run in two steps. A GET request shows the empty or filled form. A POST request (the user pressing Save) checks the form, saves it, and redirects to `success_url`. If the form has an error, the same page is shown again with the messages.

### The API viewset

`ModelViewSet` provides list, create, retrieve, update, partial update and delete in a few lines. You supply the `queryset` (which rows) and the `serializer_class` (how to convert them). The router in `urls.py` creates the URLs for you.

### The names that must match

| In the view | Used in the template or URL |
| --- | --- |
| `'Home.html'`, `'Book_rental_list.html'`, `'Rental_detail.html'`, `'form.html'`, `'delete.html'` | The real filenames in `Templates/` |
| `{'RBooks': ...}` | `{% for RBook in RBooks %}` |
| `{'bookrental': ...}` | `{{ bookrental.book_title }}` |
| `context_object_name = 'bookrental'` | `{{ bookrental.book_title }}` in `delete.html` |
| `reverse_lazy('bookrental')` | `name='bookrental'` in `urls.py` |
| Parameter `rid` | `<int:rid>` in the URL |
| Class views read `pk` | `<int:pk>` in the URL |

## Part 5: The two urls.py files

There are two URL files, and the connection between them is where beginners lose time. The project file is the front door and the app file is the room list.

### LBRS_Project/urls.py (the project file)

```python
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('', include('BookRental_app.urls')),
]
```

- `path('admin/', ...)` sends everything starting with `/admin/` to Django's admin.
- `path('', include('BookRental_app.urls'))` sends every other URL to your app's URL file. The empty `''` means no prefix, so the app's URLs start at the site root.
- The text inside `include()` is a Python path to the file. `'BookRental_app.urls'` means the file `urls.py` in the folder `BookRental_app`. A wrong spelling gives `ModuleNotFoundError`.
- Django reads the list top to bottom and stops at the first match.

### BookRental_app/urls.py (the app file)

```python
from django.urls import path, include
from rest_framework.routers import DefaultRouter
from . import views

router = DefaultRouter()
router.register('Book_rental', views.BookRentalViewSet, basename='Book_rental')

urlpatterns = [
    path('', views.Home, name='Home'),
    path('Book_rental_list/', views.Book_rental_list, name='bookrental'),
    path('Rental_detail/<int:rid>/', views.Rental_detail, name='rental_detail'),
    path('Add_rental/', views.Add_rental.as_view(), name='Add_rental'),
    path('Update_rental/<int:pk>/', views.Update_rental.as_view(), name='Update_rental'),
    path('Delete_rental/<int:pk>/', views.Delete_rental.as_view(), name='Delete_rental'),
    path('api/', include(router.urls)),
    path('api-auth/', include('rest_framework.urls')),
]
```

Each `path()` has three parts:

1. **The URL pattern**, for example `'Book_rental_list/'`. This is what the browser shows.
2. **The view**, for example `views.Book_rental_list`. This must be a real name in `views.py`.
3. **The name**, for example `name='bookrental'`. This is the label that templates and `reverse_lazy` use, so you never type the URL by hand.

Things to notice:

- Class views are written with `.as_view()`. Function views are not.
- `<int:rid>` captures a whole number from the URL and passes it to the view as the argument `rid`. `<int:pk>` does the same with the name `pk`.
- `router.register('Book_rental', ...)` creates the API URLs `api/Book_rental/` and `api/Book_rental/<id>/`. The `basename` gives them the route names `Book_rental-list` and `Book_rental-detail`, which the tests use.
- `path('api-auth/', include('rest_framework.urls'))` adds the login and logout pages for the browsable API at `/api-auth/login/`.

### The route table you get

| URL | View | Route name | Shows |
| --- | --- | --- | --- |
| `/` | `Home` | `Home` | Welcome page |
| `/Book_rental_list/` | `Book_rental_list` | `bookrental` | All rentals |
| `/Rental_detail/3/` | `Rental_detail` | `rental_detail` | Rental number 3 |
| `/Add_rental/` | `Add_rental` | `Add_rental` | Empty form |
| `/Update_rental/3/` | `Update_rental` | `Update_rental` | Form filled with rental 3 |
| `/Delete_rental/3/` | `Delete_rental` | `Delete_rental` | Delete confirmation |
| `/api/Book_rental/` | `BookRentalViewSet` | `Book_rental-list` | JSON list (login required) |

### Where NoReverseMatch comes from

It means a template or view asked for a route name that does not exist, or gave it the wrong arguments. The usual causes:

- The name in `{% url 'bookrental' %}` is spelled differently from `name='bookrental'`. Names are case-sensitive, so `'home'` is not `'Home'`.
- The route needs an argument and the tag gave none, for example `{% url 'rental_detail' %}` without the id.
- The route takes an argument and you passed the wrong kind, for example text instead of a number for `<int:rid>`.
- You added `app_name = 'BookRental_app'` to the app's `urls.py`. After that, every name needs the prefix: `{% url 'BookRental_app:bookrental' %}`. You have not added it, so your names have no prefix.

## Part 6: The templates

A template is an HTML file with Django tags mixed in. The view fills it with data, and Django returns plain HTML. Your six templates share one layout through inheritance.

### The three kinds of template syntax

| Syntax | Purpose | Example |
| --- | --- | --- |
| `{{ ... }}` | Print a value | `{{ bookrental.book_title }}` |
| `{% ... %}` | Run an instruction | `{% for %}`, `{% if %}`, `{% url %}`, `{% extends %}` |
| `{# ... #}` | A comment that is removed | `{# note to myself #}` |

Do not use `<!-- -->` to hide template code. The browser ignores it, but Django still runs every tag inside it.

### base.html: the shared layout

It holds everything that is the same on every page: the head, the navbar, the footer and one empty slot.

```html
{% load static %}
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>{% block title %}Library Rental System{% endblock %}</title>
    <link rel="stylesheet" href="{% static 'css/style.css' %}">
</head>
<body>
    <nav class="navbar">
        <h2>Library Rental System</h2>
        <div>
            <a href="{% url 'Home' %}">Home</a>
            <a href="{% url 'bookrental' %}">Rentals</a>
            <a href="{% url 'Add_rental' %}">Add Rental</a>
        </div>
    </nav>

    <main class="container">
        {% block content %}
        {% endblock %}
    </main>

    <footer><p>&copy; 2026 Library Rental System</p></footer>
    <script src="{% static 'js/script.js' %}"></script>
</body>
</html>
```

- `{% load static %}` must come before any `{% static %}`. It switches on that tag.
- `{% static 'css/style.css' %}` builds the URL of a file inside your `static/` folder. The path after `static/` must match the real path.
- `{% url 'Home' %}` builds the URL from the route name, so a link never breaks if you change the URL text.
- `{% block content %}` is the empty slot. Each child page fills it.

### The child pages

Every other page starts with `{% extends 'base.html' %}` and puts all its content inside `{% block content %}`. Anything outside a block is ignored.

| Template | Shows | Data it reads |
| --- | --- | --- |
| `Home.html` | Welcome section and a button | None |
| `Book_rental_list.html` | One link per rental, or "No rentals found." | `RBooks` |
| `Rental_detail.html` | Every field of one rental, plus Edit and Delete buttons | `bookrental` |
| `form.html` | The add and edit form | `form` (given by the class view) |
| `delete.html` | The confirmation question and a Delete button | `bookrental` |

The list page is the best example of how the parts connect:

```html
{% extends 'base.html' %}

{% block title %}Rental List{% endblock %}

{% block content %}
<h1>Book Rental List</h1>
<div class="card">
    {% for RBook in RBooks %}
        <div class="book-item">
            <a href="{% url 'rental_detail' RBook.id %}">{{ RBook.book_title }}</a>
        </div>
    {% empty %}
        <p>No rentals found.</p>
    {% endfor %}
    <a href="{% url 'Add_rental' %}" class="btn">Add rental</a>
</div>
{% endblock %}
```

- `RBooks` is the key the view sent. `RBook` is a temporary name for one rental inside the loop.
- `{% url 'rental_detail' RBook.id %}` gives the route name and the one argument it needs, so it builds `/Rental_detail/5/`.
- `{% empty %}` runs only when the list has no items.

### The form pages

```html
<form method="POST">
    {% csrf_token %}
    {{ form.as_p }}
    <button type="submit" class="btn">Save</button>
</form>
```

- `method="POST"` sends the data to the same URL that showed the form, and the class view handles it. No `action` is needed.
- `{% csrf_token %}` adds a hidden security code. Without it, every POST is rejected with a 403 error. It must be inside the `<form>` tags.
- `{{ form.as_p }}` prints every form field, each wrapped in a paragraph, along with its error messages. `form` is the name the class view gives the form automatically.
- On the delete page, the same form pattern is used with only a button, because a delete is a POST too. It reads `{{ bookrental.book_title }}` because the view sets `context_object_name = 'bookrental'`.

### Static files

`static/css/style.css` and `static/js/script.js` are loaded by `{% static %}` in `base.html`. Because `STATICFILES_DIRS` points at your `static/` folder, Django can serve them during development.

## Part 7: Admin, API, permissions and the daily command

These are the parts that work beside your pages: a ready-made management screen, a JSON interface, a login rule, and a command that keeps overdue data fresh.

### admin.py

```python
from django.contrib import admin
from .models import BookRental

@admin.register(BookRental)
class BookRentalAdmin(admin.ModelAdmin):
    list_display = ('book_title', 'borrower_name', 'status', 'return_date', 'fine_amount')
    readonly_fields = ('fine_amount', 'returned_date')
```

- `@admin.register(BookRental)` puts the model in the admin at `/admin/`, where you can add, edit and delete rows without writing any page.
- `list_display` chooses the columns of the list. The names must match model fields.
- `readonly_fields` is needed for fields with `editable=False`. Without it, the admin hides them completely.
- To log in you need an account: run `python manage.py createsuperuser` once. The login page itself comes with Django, so you write no login files.

### The REST API

The API gives programs (a phone app, a script) the same data as JSON, instead of HTML pages. Three pieces make it work, and you already met them:

1. `BookRentalSerializers` in `serializers.py` converts a rental to JSON and back, and validates it.
2. `BookRentalViewSet` in `views.py` provides list, create, read, update, partial update and delete.
3. `router.register('Book_rental', ...)` in `urls.py` builds the URLs under `/api/`.

Open `/api/` in a browser for the index, and `/api/Book_rental/` for the list. The browsable API page shows a form for creating and editing records.

### Permissions

Django REST Framework lets everyone in by default. This block in `settings.py` changes that for the whole project:

```python
REST_FRAMEWORK = {
    'DEFAULT_PERMISSION_CLASSES': [
        'rest_framework.permissions.IsAuthenticated',
    ],
}
```

Only a logged-in user can now use the API, which matters because the data includes borrower emails. Log in at `/api-auth/login/` or `/admin/` with an account made by `createsuperuser`. The normal pages (`/Book_rental_list/` and the others) still need no login. Locking those would need a login page, a `LOGIN_URL` setting and `LoginRequiredMixin` on the class views, which this project does not have yet.

### The update_overdue command

A status and fine only update when a rental is saved. A rental nobody opens would still say "Borrowed" the day after it is due. This command saves every open rental again so the numbers are fresh:

```python
# BookRental_app/management/commands/update_overdue.py
from django.core.management.base import BaseCommand
from BookRental_app.models import BookRental


class Command(BaseCommand):
    help = "Refresh status and fine for all rentals that are still open"

    def handle(self, *args, **options):
        count = 0
        for rental in BookRental.objects.exclude(status__in=['Returned', 'Lost']):
            rental.save()
            count += 1
        self.stdout.write(self.style.SUCCESS(f'Updated {count} rentals'))
```

Run it with `python manage.py update_overdue`. The file name (`update_overdue`) becomes the command name. The folders `management/` and `management/commands/` each need an empty `__init__.py`, or Django does not find the command. Run it once a day; on Windows, Task Scheduler can do that for you.

## Part 8: Putting it together

### One full journey: adding a rental

1. You click **Add Rental** in the navbar. The link was built by `{% url 'Add_rental' %}`, so it points to `/Add_rental/`.
2. `LBRS_Project/urls.py` sees no `admin/` prefix and passes the URL to `BookRental_app.urls`.
3. The route `path('Add_rental/', views.Add_rental.as_view(), name='Add_rental')` matches and calls the `Add_rental` class view.
4. This is a GET request, so the view builds an empty `BookRentalForm` and renders `form.html` with it as `form`.
5. `form.html` extends `base.html`, so you see the navbar and footer, and `{{ form.as_p }}` prints the input boxes.
6. You fill in the form and press Save. The browser sends a POST to the same URL, with the hidden `{% csrf_token %}` value.
7. The view runs `BookRentalForm`. It checks each field, then runs `clean()` to compare the two dates.
8. If something is wrong, the same page comes back with error messages. If all is well, the form calls `BookRental.save()`.
9. The model's `save()` runs `update_status_and_fine()`, sets the status and fine, and writes one row to MySQL.
10. The view redirects to `success_url`, which is `reverse_lazy('bookrental')`, so you land on `/Book_rental_list/` and see the new title in the list.

### The exact-name cheat sheet

Every pair below must be spelled identically, including capitals and underscores.

| Write it here | Use it here |
| --- | --- |
| App folder name `BookRental_app` | `INSTALLED_APPS`, `include('BookRental_app.urls')`, `name` in `apps.py`, imports in the management command |
| Route `name='bookrental'` in the app `urls.py` | `{% url 'bookrental' %}` and `reverse_lazy('bookrental')` |
| Route names `Home`, `rental_detail`, `Add_rental`, `Update_rental`, `Delete_rental` | The `{% url '...' %}` tags in the templates |
| URL parameter `<int:rid>` | The argument `rid` in `def Rental_detail(request, rid)` |
| URL parameter `<int:pk>` | Class views (they always look for `pk`) |
| Template filename passed to `render()` or `template_name` | The real file in `Templates/` |
| Context key `'RBooks'` | `{% for RBook in RBooks %}` |
| Context key `'bookrental'` or `context_object_name` | `{{ bookrental.field }}` in the template |
| Model field names | `forms.py` widgets, `admin.py` lists, `{{ obj.field }}` in templates |
| `{% extends 'base.html' %}` | The real filename `base.html` |
| `{% block content %}` in a child | `{% block content %}` in `base.html` |
| `{% static 'css/style.css' %}` | The real path `static/css/style.css` |
| `basename='Book_rental'` in the router | `reverse('Book_rental-list')` in tests |
| `REST_FRAMEWORK` in settings | Exactly that name, in capitals |

### Common errors and what they mean

| Error | Usual cause | Fix |
| --- | --- | --- |
| `NoReverseMatch` | A `{% url %}` name or argument does not match a route | Compare the name with `name=` in `urls.py`, and check the arguments |
| `TemplateDoesNotExist` | Wrong filename in `render()`, or the folder is not in `DIRS` | Check the spelling and the `DIRS` setting |
| `TemplateSyntaxError: block appears more than once` | Two `{% block content %}` in one file, often from pasting twice | Keep one copy in each file |
| `CSRF verification failed` (403) | `{% csrf_token %}` is missing from a POST form | Add it inside the `<form>` |
| `Unknown column ... in field list` | The model changed but migrations were not run | `makemigrations`, then `migrate` |
| `No changes detected` | The app is missing from `INSTALLED_APPS` | Add `'BookRental_app'` |
| `KeyError: 'SECRET_KEY'` | There is no `.env` file, or the name is misspelled | Create `.env` from your `.env.example` |
| `Access denied ... to database 'test_...'` | MySQL user cannot create the test database | Grant privileges on `test\_%`.* |
| Style not applied | `{% load static %}` missing, or the CSS path is wrong | Check the first line and the path |
| 404 on `/Rental_detail/99/` | No rental has that id | Expected; the view returns a 404 page |
